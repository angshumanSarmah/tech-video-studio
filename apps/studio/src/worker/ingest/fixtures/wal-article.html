How a write-ahead log keeps a database honest

By a staff engineer at Example Engineering Notes

A database promises that a committed write survives a crash. The write​-ahead log is how it keeps that promise: every change is appended to a sequential log on disk before the change touches the data pages. If the process dies halfway through updating a page, recovery replays the log and the page ends up exactly as the commit said. Appending is cheap because the disk head, or the SSD's flash translation layer, never has to seek. In our example benchmark a single log device sustained 48,000 fsync-batched commits per second, while random page writes on the same device topped out near 6,000.

Group commit

Calling fsync for every transaction would cap throughput at the device's flush rate. Group commit batches the log records of many transactions into one flush. A transaction waits a few hundred microseconds for company, then all of them are acknowledged together once the flush returns.

What recovery does

  1. Find the last checkpoint record in the log.
  2. Redo every logged change after the checkpoint.
  3. Undo the changes of transactions that never committed.

The log is not a backup. It is truncated after every checkpoint, so it only ever holds the changes the data pages might not have yet. Backups and replicas are separate tools built on top of the same stream of records.
